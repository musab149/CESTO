# Staging environment

A complete tester sandbox: API, web, and admin, all hooked to a Neon staging
database that mirrors the schema of prod. Pushes to the `staging` git branch
deploy everything automatically. Production (master branch + cesto-* prod
projects) is never touched.

## Architecture at a glance

```
  staging branch ──┬──→ Render: cesto-api-staging ──→ Neon: staging branch
                   ├──→ Vercel: cesto-web-staging
                   └──→ Vercel: cesto-admin-staging
```

## Final staging URLs

- API   → `https://cesto-api-staging.onrender.com`
- Web   → `https://cesto-web-staging.vercel.app`
- Admin → `https://cesto-admin-staging.vercel.app`

These are what you share with testers.

## One-time setup (do once, then forget)

### 1 · Create the `staging` git branch

```bash
git checkout master
git pull
git checkout -b staging
git push -u origin staging
```

From now on:
- Merge `master` → `staging` whenever you want testers to see the latest.
- Open PRs from feature branches into `master`. They auto-deploy to Vercel
  preview URLs for your own review; staging is only refreshed when you
  intentionally merge to `staging`.

### 2 · Create a Neon branch for the staging database

In the Neon console:

1. Open the project the prod DB lives in.
2. **Branches → Create branch** → name it `staging`, branch from `main`.
3. Copy the connection string (looks like
   `postgresql://...neon.tech/...?sslmode=require`).

This is your `DATABASE_URL` for the staging API. Neon branches share storage
at first, so it's free on the same plan.

> **Why a branch and not a separate project?** Branches are instant, share
> billing, and you can reset by deleting and re-creating in 5 seconds. A
> separate project would be overkill.

### 3 · Provision the staging API on Render

The blueprint already declares `cesto-api-staging` — Render will pick it up
on the next sync.

1. Render dashboard → **Blueprints → Resync** on the existing `cesto-api`
   blueprint.
2. Render detects the new `cesto-api-staging` service and prompts for env
   vars. Paste:
   - `DATABASE_URL` → the Neon `staging` branch connection string
   - `BUNNY_STORAGE_ZONE`, `BUNNY_STORAGE_KEY`, `BUNNY_CDN_URL` (and
     `BUNNY_STORAGE_HOST` only if the zone is not in Frankfurt)
     → use a SEPARATE storage zone from prod: testers upload junk, and a
     shared zone means prod pays to store it forever (there is no orphan
     purge for Bunny yet). `BUNNY_CDN_URL` must include `https://`.
     Bunny Optimizer is deliberately NOT enabled — delivery uses
     pre-generated width variants instead, so there is nothing to switch
     on in the pull zone. See docs/BUNNY_ROLLOUT.md for the full sequence;
     the migration and the variant backfill both have to be run against
     the staging database before the app is used.
3. JWT secrets are auto-generated by `generateValue: true` — leave alone.
4. First build runs `prisma migrate deploy` then `prisma/seed-essentials.ts`.
   That script creates **only the admin user** — no categories, no
   products, no demo orders. Testers populate everything via the admin
   panel, making this a true clean sandbox.

   - **Email:** `admin@groceryapp.es`, or whatever `ADMIN_SEED_EMAIL` is
     set to on the Render service.
   - **Password:** whatever `ADMIN_SEED_PASSWORD` is set to in the Render
     dashboard for `cesto-api-staging`. There is no default and no
     fallback — if it is unset or shorter than 10 characters the script
     logs a warning and **skips creating the admin entirely**, so a
     missing value looks like a broken login rather than a broken seed.
     Changing it there rotates the password on the next deploy.

   > This used to document `admin1234`. That is nine characters, so it
   > would be refused by the ten-character minimum — it predates the
   > ADMIN_SEED_PASSWORD requirement and never worked after it landed.

> **Why a separate seed file?** `prisma db seed` (used locally) runs the
> full demo dataset — perfect for dev, wrong for a fresh tester sandbox.
> `seed-essentials.ts` is the staging variant: idempotent (upsert by email)
> and rerun-safe on every deploy. Local dev keeps using the full seed
> through `npm run seed`.

### 4 · Provision the two staging Vercel projects

For each of web and admin:

1. Vercel dashboard → **Add New → Project**.
2. Import the same `outis-9/cesto` repo.
3. **Project name**: `cesto-web-staging` (or `cesto-admin-staging`).
4. **Root directory**: `apps/web` (or `apps/admin`).
5. **Production branch**: `staging` *(this is the key change vs. prod)*.
6. **Environment variables → Production**:
   - `VITE_API_URL` = `https://cesto-api-staging.onrender.com`
7. Deploy.

> **Why separate projects, not preview URLs?** A stable URL testers can
> bookmark, predictable CORS allow-listing on the API, and zero confusion
> between "the staging site" and "every open PR".

### 5 · Verify

- Open `https://cesto-api-staging.onrender.com/api/health` → expect a 200.
- Open the staging web URL → home page renders, products load.
- Open the staging admin URL → sign in works.

If CORS fails, double-check the `CORS_ORIGINS` env var on the staging API
matches the exact Vercel hostnames (no trailing slash).

## Day-to-day workflow

| Action                                | Effect                                                |
| ------------------------------------- | ----------------------------------------------------- |
| Push to a feature branch              | Vercel preview URLs only (your own review)            |
| Merge feature → `staging`             | Staging API + web + admin redeploy. Testers see it.   |
| Merge feature → `master`              | Production deploys. Customers see it.                 |
| Merge `master` → `staging`            | Bring staging up to date with prod.                   |
| Reset staging DB                      | Delete Neon `staging` branch, re-create from `main`.  |

## Resetting the staging database

Testers will dirty the DB over time. Two options:

**Fast reset (recommended)**: Neon console → Branches → delete `staging`,
re-create from `main`. Restart the Render staging service so it re-runs
migrations + `seed-essentials.ts`. You're back to "admin only, empty
catalogue" in under a minute.

**Surgical**: Connect with `psql` via the Neon connection string and run
the SQL you need.

> If you ever want staging to come up with the full demo catalogue instead
> of empty, swap `prisma/seed-essentials.ts` for `npx prisma db seed` in
> the staging `buildCommand` in `render.yaml`.

## Adding env vars

Both Render services and both Vercel projects have separate env-var stores.
When you add a new var:

- Backend var → set on both `cesto-api` *and* `cesto-api-staging` in Render.
- Frontend var → set on each Vercel project under the environment you care
  about (Production = the branch that project tracks).
- Document it in the relevant `.env.example` so the next engineer knows it
  exists.
